# M3 local network control — 2026-10-21

## Implementation

- `MiIoLanTransport` speaks miIO over UDP 54321: 32-byte big-endian header, handshake with
  `0xFFFFFFFF` fields, AES-128-CBC (key `MD5(token)`, IV `MD5(key || token)`), checksum
  `MD5(header[0:16] || token || ciphertext)`, request JSON terminated with `\0`, response NULs
  stripped before parsing.
- Responses are validated before decryption: exact datagram length, device id, checksum
  (constant-time compare). The UDP socket is connected to the device endpoint.
- Device-level rejections (`set_properties` entry codes, `action` result code) throw
  `MiHomeException` with `IsDeviceError = true`, matching the cloud client.
- `LanOutcomeUnknownException` means the action packet was sent but no verified reply arrived;
  it is never retried and never falls back, because the action may already have run.
- Routing: channel guard first; LAN only when the device has a **private** address, a token in
  the in-memory secret store, and no active failure block. `LanUnavailableException` falls back
  to the cloud and blocks the device for five minutes; a LAN success clears the block. Tokens
  never enter `MiDevice`, logs, or `LanEndpoint.ToString()`.

## Review

| # | Sev | Finding | Resolution |
| --- | --- | --- | --- |
| 1 | P1 | Checksum was computed with a zeroed slot instead of the token. | `MD5(header[0:16] || token || ciphertext)`, with a fixed vector test. |
| 2 | P1 | LAN writes and actions ignored operation-level codes. | Entry/inner codes now surface as device errors; action returns `out` or `[]`. |
| 3 | P1 | An action could run twice when the reply was lost. | Post-send failures throw `LanOutcomeUnknownException`; no retry, no cloud fallback. |
| 4 | P2 | Responses were decrypted without validating length, sender, checksum. | Full validation before decryption; connected socket; tamper/did/length tests. |
| 5 | P2 | The miIO NUL terminator was not handled. | Added on encrypt, stripped on decrypt, with tests. |
| 6 | P2 | Handshake stamp was discarded. | Documented as UTC seconds; device-specific stamp bases remain unverified. |
| 7 | P3 | `LanEndpoint.ToString()` printed the token. | Masked. |

## Live status: NOT verified end-to-end

A raw UDP handshake to three devices on the same `/24` as the PC got no reply at all, so the
transport has not been exercised against real hardware. The absence of a reply does not prove a
code defect: AP isolation, a different VLAN, a firewall or a device with LAN control disabled
all produce the same symptom.

Verification still required on a reachable network:

1. handshake round-trip (device id and stamp);
2. a read-only property read;
3. a user-approved idempotent write with read-back;
4. split-channel parent DID/token/IP combination;
5. IPv6 link-local scope handling.

Until then the client stays cloud-first in practice: a failed LAN probe costs one timeout and
blocks LAN for that device for five minutes.
